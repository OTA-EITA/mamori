# v0.3 design

v0.2 made mamori usable day to day. v0.3 makes joining and leaving the company one change: when an admin adds someone to mamori, or disables them, the SaaS tools follow. It also lets another system (an HR tool, or an IdP mamori sits behind) manage mamori's users through SCIM.

There are two directions, and they are separate features:

| Direction | What | Standard |
|---|---|---|
| Inbound | Another system creates, updates and disables users and groups in mamori | SCIM 2.0 server (RFC 7643, RFC 7644) |
| Outbound | mamori creates, updates and suspends accounts in Google Workspace and Slack | Google Directory API; Slack SCIM 2.0 |

## SCIM 2.0 server (inbound)

Base path `/scim/v2`. Supported:

- `Users` and `Groups`: `GET` (list with `filter`, `startIndex`, `count`), `GET /{id}`, `POST`, `PUT`, `PATCH`, `DELETE`
- `ServiceProviderConfig`, `ResourceTypes`, `Schemas`
- Filters: `eq` on `userName`, `externalId`, `emails.value` and (groups) `displayName`, joined with `and`. Anything else returns `400` with `scimType: "invalidFilter"`, so a client never silently gets the wrong list.
- Not supported (stated in `ServiceProviderConfig`): bulk, sorting, ETags, password changes.

Attribute mapping:

| SCIM | mamori |
|---|---|
| `userName` | email (also the first `emails` value) |
| `name.formatted`, or `name.givenName` + `name.familyName`, or `displayName` | name |
| `active` | not disabled |
| `externalId` | stored as is, for the client's own matching |
| Group `displayName` | group name |
| Group `members[].value` | user ids |

Behaviour:

- `active: false` disables the user and signs them out everywhere, the same as the admin console.
- `DELETE /Users/{id}` disables the user and marks them deleted: they no longer appear in SCIM results (`404`), but their audit history stays. They can be restored only from the admin console.
- `PATCH` accepts the forms Microsoft Entra ID and Okta send: operations with and without `path`, `"op": "Replace"` in any case, and `"value": "False"` as a string.
- Users created through SCIM get no password. They sign in after the admin sends a setup link, or with a passkey set up through that link.

Authentication: bearer tokens that an admin creates in the console (or with the CLI), shown once and stored as SHA-256. Each has a name and a last-used time. Every change made through SCIM is in the audit log with `actor.type: "scim"` and the token name.

## Outbound provisioning

### Who is provisioned

Each connector is tied to one mamori group (`"group": "google-workspace"` in its config). Members of that group who are active get an account; everyone else does not. So access is managed in one place, in mamori's groups, and a leaver is handled by disabling them in mamori.

| Event in mamori | Action at the SaaS |
|---|---|
| Active user added to the group, or a member enabled | Create the account, or reactivate it |
| Name or email changed | Update |
| Removed from the group, disabled, or deleted | Suspend (Google) / deactivate (Slack). Never delete. |

Never deleting is deliberate: Google keeps a deleted user for 20 days only, and Slack does not delete users at all. Suspension keeps the data for whatever the company's offboarding process decides.

### How changes are sent

- Every change in mamori writes jobs to a `provisioning_jobs` table in the same transaction. A worker in the same process sends them, retries failures with exponential backoff (up to 24 hours), and respects `Retry-After` on `429`.
- Jobs are idempotent: before creating, a connector looks the account up by email, so a retry after a timeout does not create a duplicate.
- `provisioning_links` keeps, per connector and user, the external id and the last state sent.
- `mamori-admin provision reconcile <connector> [--apply]` compares mamori with the SaaS and lists what would change; with `--apply` it queues those changes. This catches anything changed by hand at the SaaS.
- The admin console shows each connector's pending and failed jobs with the last error.
- Credentials are read from files named in the config, never from the database, and never appear in the audit log.

### Google Workspace

- API: Admin SDK Directory API, `https://admin.googleapis.com/admin/directory/v1/users`.
- Auth: a service account with domain-wide delegation, scope `https://www.googleapis.com/auth/admin.directory.user`, acting as an admin named in the config. mamori signs the JWT itself (RS256 with `node:crypto`), so there is no Google client library.
- Create: `primaryEmail`, `name.givenName` / `name.familyName`, and a random password, which Google requires. Nobody uses that password: Google Workspace accepts mamori as a third-party IdP through a custom OIDC profile, so people sign in to Google with mamori (see `docs/google-sso.md`).
- Leave: `suspended: true`. Come back: `suspended: false`.

### Slack

- API: Slack SCIM 2.0, `https://api.slack.com/scim/v2`. Only available on Business+ and Enterprise plans; mamori checks this when the connector starts and reports it clearly.
- Auth: a token with the `admin` scope, from a file.
- Leave: `DELETE /Users/{id}`, which deactivates (Slack never deletes users). Come back: `PATCH` with `active: true`.

## Testing

The connectors are tested against small fake Google and Slack servers in the test suite that check every request (paths, auth headers, bodies) and can return errors, `429` and timeouts. No test calls the real services.

## Order of work

1. SCIM tokens (console page, CLI) and the SCIM `Users` endpoints
2. SCIM `Groups` and the discovery endpoints
3. The provisioning queue, worker and links tables, with a fake connector
4. Slack connector
5. Google Workspace connector
6. Console page for connector status, and `provision reconcile`

## Open questions

- Should removing someone from a connector's group suspend them at once, or after a grace period, in case of mistakes? Current plan: at once, because a leaver's access should end quickly, and reactivation is one click.
- Google requires a password at creation. It is random and never stored or shown; people sign in with mamori through Google's OIDC SSO profile (`docs/google-sso.md`). Whether Google sends PKCE, and how super admins sign in, still has to be checked on a real Workspace.
