# v0.2 design

v0.1 can sign people in. v0.2 makes mamori something a small company can run day to day: people set up their own passkeys and TOTP, an admin manages users and groups in a browser, MFA can be required, and every sign-in and admin change is in an audit log.

## Fixes to v0.1 that come first

- **Proxy headers are trusted unconditionally.** v0.1 sets `provider.proxy = true`, so any client can send `X-Forwarded-For` / `-Proto` / `-Host` and have it believed. v0.2 adds `trustProxy` to the config, default `false`, and uses the same flag for the client IP in the audit log.
- **Disabling a user does not end their sessions.** `findAccount` refuses disabled users, so new tokens are not issued, but an existing sign-in session and refresh tokens stay in the database. v0.2 stores `account_id` on `oidc_models` and, when a user is disabled or their MFA is reset, deletes their sessions and revokes their grants.
- **Lockout can be used to lock other people out.** v0.1 locks an email after 10 failures from anywhere, so anyone who knows an address can keep that person out. v0.2 changes this (see "Sign-in throttling").

## Scope

1. Passkeys (WebAuthn) for sign-in and as a second factor
2. Self-service account page: register and remove passkeys and TOTP, download recovery codes
3. An MFA policy that can require every user to have a second factor
4. Groups, and a `groups` claim for apps that map groups to roles
5. Audit log, stored and written as JSON lines
6. Admin console in the browser: users, groups, audit log
7. Schema migrations

Out of scope for v0.2: managing OIDC clients in the console (they stay in the config file), SCIM, SAML, email delivery, password reset by email.

## How the console and account page sign in

The account page and the admin console are an OIDC client of mamori itself, registered automatically as `mamori-console`. They go through the same authorization code + PKCE flow as any other app.

- One sign-in code path. The throttling, MFA policy and audit log apply to the console without extra code.
- The console keeps its own session: an HTTP-only, `SameSite=Lax` cookie holding a random id, with the session row (user id, `amr`, CSRF token, expiry) in SQLite. Idle timeout 30 minutes, absolute timeout 8 hours.
- Admin pages need `is_admin` on the user **and** an `amr` that includes a second factor. An admin who signed in with a password only is sent back to sign in again.
- Every POST in the console carries a CSRF token tied to the console session. The session id is replaced at sign-in.
- Signing out ends the console session and then the mamori session through RP-initiated logout (`end_session`), so the next visit asks for credentials again.
- The sign-in forms themselves (`/interaction/...`) do not need a separate CSRF token: oidc-provider's interaction cookie is `SameSite=Lax`, so a form posted from another site arrives without it and is rejected.

## Passkeys

Library: [`@simplewebauthn/server`](https://github.com/MasterKale/SimpleWebAuthn).

- RP ID is the issuer's host name, and the expected origin is the issuer origin. If the issuer changes host, existing passkeys stop working; this is stated in the docs.
- Registration requires user verification and asks for a discoverable credential (resident key), so people can sign in without typing an email.
- Stored per credential: credential id, public key, sign counter, transports, backup eligible / backed up flags, a name the user chose, created and last used times.
- The counter is checked by `@simplewebauthn/server` when either side is non-zero; it throws when the new value is not greater than the stored one. mamori catches that case, fails the sign-in and writes `passkey.counter_regressed`.
- Usernameless sign-in needs JavaScript on the login page. The script is served as a static file from mamori, and the CSP becomes `script-src 'self'`; there is still no inline script.

Sign-in options on the login page:

| Method | First factor | Second factor | `amr` (RFC 8176) |
|---|---|---|---|
| Passkey | passkey with user verification | not needed | `["hwk", "mfa"]` or `["swk", "mfa"]` |
| Password, then passkey | password | passkey | `["pwd", "hwk", "mfa"]` or `["pwd", "swk", "mfa"]` |
| Password, then TOTP | password | TOTP | `["pwd", "otp", "mfa"]` |
| Password, then recovery code | password | recovery code | `["pwd", "otp", "mfa"]` |
| Password only | password | none | `["pwd"]` |

`mfa` is added whenever two independent factors were used, so apps can check one value. A passkey with user verification counts as two factors on its own (something you have, and a PIN or biometric). Recovery codes are one-time codes, so they report `otp` like TOTP; the audit log tells them apart.

RFC 8176 separates a hardware-secured key (`hwk`) from a software-secured key (`swk`). Synced passkeys (iCloud Keychain, Google Password Manager) leave the device, so mamori reports `swk` when the authenticator says the credential is backed up and `hwk` otherwise.

## MFA policy

`mfa: "optional" | "required"` in the config, default `"required"` for new installs.

With `"required"`, a user who has no second factor signs in with the password and is then taken to a setup step inside the same sign-in: add a passkey or TOTP, save the recovery codes, then continue to the app. They cannot skip it. The ID token carries `mfa` from that sign-in on.

## Recovery codes

Ten codes of 10 characters from an alphabet without look-alike characters (about 50 bits each), shown once. They are stored as HMAC-SHA256 with a server key kept in `settings`, not as scrypt: checking a code means comparing against up to ten hashes, and ten scrypt runs per attempt would be an easy way to load the server. The entropy of the codes and the sign-in throttling make a fast hash enough here. Each code works once. Using one is written to the audit log, and the account page shows how many are left. An admin can also reset a user's second factors, which forces the setup step at the next sign-in.

## Sign-in throttling

Replaces the v0.1 lockout.

- Per email and client IP: after 10 failures in 15 minutes, that IP is locked out for that email for 15 minutes.
- Per email from any IP: each failure after the fifth adds a delay before the answer (1, 2, 4 ... seconds, at most 30). The account itself is never locked, so the owner can still sign in, and a passkey sign-in is not slowed down.
- Both counters stay in memory for now (one instance).

## Creating users from the console

Admins do not set passwords. Creating a user in the console makes a setup link (random token, valid for 24 hours, shown once) that the admin passes to the person over chat. The link lets them choose a password and set up a second factor, and stops working after use. The CLI keeps `user add` with a password from stdin for the first admin.

## Groups

Tables `groups (id, name, description)` and `group_members (group_id, user_id)`. A new scope `groups` adds a `groups` claim with the group names to the ID token and userinfo. Group names are what apps see, so renaming a group is a breaking change for them; the console warns about this.

## Audit log

Every event is one row in `audit_events` and one JSON line on stdout (or a file set in the config), so it can go to CloudWatch, Datadog or Loki without a plugin.

```json
{"time":"2026-11-02T01:23:45.678Z","event":"sign_in.failed","actor":{"type":"user","email":"alice@example.co.jp"},"client_id":"intranet","ip":"203.0.113.9","user_agent":"Mozilla/5.0 ...","reason":"wrong_password"}
```

Events:

| Area | Events |
|---|---|
| Sign-in | `sign_in.succeeded`, `sign_in.failed` (reason), `sign_in.throttled`, `mfa.challenge_failed`, `passkey.counter_regressed`, `sign_out` |
| Tokens | `token.issued`, `token.revoked`, from oidc-provider's `access_token.issued`, `refresh_token.issued`, `grant.revoked` and `end_session.success` events |
| Self-service | `passkey.added`, `passkey.removed`, `totp.added`, `totp.removed`, `recovery_codes.generated`, `recovery_code.used`, `setup_link.used` |
| Admin | `user.created`, `setup_link.created`, `user.disabled`, `user.enabled`, `user.mfa_reset`, `group.created`, `group.member_added`, `group.member_removed`, `admin.granted`, `admin.revoked` |

Never logged: passwords, codes, recovery codes, tokens, session ids. Rows older than `auditRetentionDays` (default 400, a little over a year) are deleted by the hourly cleanup.

The client IP comes from `X-Forwarded-For` only when `trustProxy` is `true` (see the fixes above).

## Admin console

Server-rendered HTML, no client-side framework, the same style as the sign-in pages. Pages:

- Users: list with search, status, MFA methods and last sign-in; create, disable and enable, reset MFA, make admin
- User detail: groups, passkeys (names and last used), recent audit events
- Groups: list, create, add and remove members
- Audit log: filter by event, user and date

## Storage changes and migrations

The schema gets a version in `PRAGMA user_version`. On start, mamori applies the numbered migrations it has not applied yet, inside a transaction, and refuses to start if the database is newer than the code. v0.1 databases are version 0 and migrate to version 1 (new tables, `users.is_admin`, `users.last_sign_in_at`).

## Order of work

0. The v0.1 fixes: `trustProxy`, ending sessions of disabled users, new throttling
1. Migrations and the audit log (everything after this writes events)
2. Console session, CSRF, and the `mamori-console` client
3. Account page with TOTP setup and recovery codes
4. MFA policy and the setup step during sign-in
5. Passkeys: registration, then sign-in
6. Groups and the `groups` claim
7. Admin console pages

## Open questions

- Is a setup link passed over chat good enough until email delivery exists? It is also how a forgotten password is handled: the admin resets the user, which revokes their sessions and issues a new link.
- Default `"required"` for the MFA policy may surprise someone upgrading from v0.1. Current plan: when the config has no `mfa` key, a database created by v0.2 uses `"required"` and a database migrated from v0.1 (schema version 0) uses `"optional"` and logs a warning at start.
- The `amr` of a password + TOTP sign-in changes from `["pwd", "otp"]` in v0.1 to `["pwd", "otp", "mfa"]`. Apps that compared the whole array need to check for `mfa` instead; this goes in the release notes.
